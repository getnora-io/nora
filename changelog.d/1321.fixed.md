**NORA raises its open-file limit at startup, so a container no longer stops accepting connections at about a thousand requests in flight (#1321)** — a container inherits the soft `RLIMIT_NOFILE` of its runtime, 1024 on a default Docker or Kubernetes node, while the hard limit there is usually 524288 or more. Every client connection and every open file takes a descriptor, so under load NORA logged `accepting a connection failed … (os error 24)` and stopped accepting: measured on 1.4.7 with 8 cores, 16 000 requests a second were served with p99 5.8 ms, and at 32 000 throughput fell to about 2 500 with 30-second timeouts. Go and the JVM raise the soft limit to the hard one when a program starts, so other registries in the same container ran with 524288; NORA now does the same on Linux, before its runtime opens anything, reads the limits from `/proc/self/limits` and logs them next to the connection limits, with a warning when the limit is below `max_connections` plus a reserve for files. The soft limit only ever moves up to the hard limit the process already has: to keep a lower ceiling, set the hard limit (`docker run --ulimit nofile=N:N`, `LimitNOFILE=N`). The systemd units, which set `LimitNOFILE=65535`, are unchanged.
