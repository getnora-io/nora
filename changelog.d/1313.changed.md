**The release SBOM describes the binary, one file per platform (#1313)** — the SPDX and CycloneDX files attached to a release came from syft scanning the checkout: the v1.4.7 CycloneDX file listed 574 components, among them dev, test and Windows-only crates (`criterion`, `proptest`, `libfuzzer-sys`, `windows-sys`) and 17 repository files, and 557 of them had no checksum and 572 no license. Trivy refused to read it. `scripts/sbom.py` now builds the files from cargo's resolver for each release target — runtime crates as `required`, proc macros and build scripts as `excluded` — with the SHA-256 of every crate from `Cargo.lock` and its license, and the release fails before any image tag moves if a file is missing a crate, lists one that is not compiled for the target, or carries a checksum that differs from `Cargo.lock`. The assets are now `nora-<tag>.sbom.amd64.{spdx,cdx}.json` and `nora-<tag>.sbom.arm64.{spdx,cdx}.json` (332 and 331 runtime crates for 1.4.7). The problem and the approach — the SBOM from the crate graph, checked against `Cargo.lock` — were proposed by @Mattbusel in #1312.
