A scheduled GC or retention pass that takes files out of the store (orphans, metadata phantoms, files evicted by `[gc] proxy_cache_max_bytes`, retention keys) marks the repository indexes stale, so the dashboard and `/api/ui/stats` count what is on disk right after the pass. They used to count the deleted files until a restart or the next write to that registry. A dry run changes nothing. `nora_artifacts_total` and the per-registry `nora_storage_bytes` were set every 60 seconds from the repository index without rebuilding it, so after a restart they read 0, and after a write or a GC/retention pass they kept the old numbers until someone opened the dashboard or `/api/ui/stats`. The 60-second update now first rebuilds the index of each enabled registry that a restart, a write or a cleanup pass marked stale — one listing of that registry — and then sets the gauges; a registry nothing touched is read from memory with no storage request. The `GC scheduler: done` line counted only orphans in its `deleted` and `bytes freed`; it now also names the files and bytes evicted by `[gc] proxy_cache_max_bytes`, separately. A scheduled retention pass with `dry_run = true` wrote a `retention-apply` entry to `audit.jsonl` although it deleted nothing; it now writes `retention-dry-run` with the bytes an applied pass would free, and a pass that deletes still writes `retention-apply`. A dry GC pass logs what it would free and evict instead of "bytes freed".
