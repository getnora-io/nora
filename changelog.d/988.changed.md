**`nora gc --apply` and `nora retention-apply --yes` warn when a server runs on the same storage (#988)** — the commands take their own publish locks, not the server's, so their deletions are not serialized with the server's publishes, and the admin guide did not say whether the server should be stopped first. Before deleting, they now print one line on stderr when a server is running on the storage, and say how to run them safely: with the server stopped, or through the server's own `[gc]` / `[retention]` schedule. On local storage the check tests the lock each server holds on its `.nora-staging/` directory from start to exit, so the staging a crashed server left behind does not warn; an object store keeps no such lock, so on S3 and GCS the commands always say they cannot tell. The commands still run: this is a warning, not a refusal. Dry runs print nothing new. The admin guide (section 5.3) now says when to use the commands and when to rely on the server's schedule, and drops the `nora gc --dry-run` flag that never existed.
