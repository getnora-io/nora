**Raw files carry annotations, and a raw PUT can copy a file in the store** — a raw `PUT` now accepts `X-Nora-Meta-<key>: <value>` headers, and `HEAD` and `GET` (full and ranged) send them back as the same headers; a `304` does not. NORA keeps the annotations with the integrity pin: as user metadata of the object on S3 and GCS (`x-amz-meta-<key>`, `x-goog-meta-<key>`), and in the entry of the key in `.nora-pins.ndjson` on local storage, where a line without annotations stays as before. A key is 1 to 64 characters from `a-z`, `0-9` and `-`, and `sha256` is the slot of the pin; a value is 1 to 1024 printable ASCII characters; a file has at most 32 annotations and 1978 bytes of keys and values, so that the pin and the annotations stay in the 2 KiB of user metadata that S3 allows. A header that breaks these rules gets a `400` that names the problem, and NORA stores nothing. The annotations are part of the file, as the bytes are: no request changes them alone, and to change them a client sends the file again with `If-Match`. A `PUT` without conditional headers to an existing file is a `200` only when the bytes and the annotations are the same as the stored ones, and a `409` when they are not. `PUT /raw/<dst>` with `X-Nora-Copy-Source: <src>` and an empty body copies `<src>` to `<dst>` in the store (S3 CopyObject, a GCS rewrite, a hard link on local storage), so the bytes do not go through NORA; `<dst>` gets the bytes, the ETag and the annotations of `<src>`, and the response carries that ETag. `If-Match` and `If-None-Match` apply to `<dst>` as they do for an upload. A copy with a body, with `X-Nora-Meta-*` headers, or with `<src>` equal to `<dst>` is a `400`, and a copy of a missing `<src>` is a `404`. The web UI shows the annotations of a raw file under its name, and `nora migrate`, `nora backup` and `nora restore` carry them with the file.
