# Руководство администратора NORA

**Версия:** 0.2.32
**Дата:** 2026-03-16
**Правообладатель:** ООО «ТАИАРС» (торговая марка АРТАИС)

---

## 1. Общие сведения

NORA — многопротокольный реестр артефактов, предназначенный для хранения, кэширования и распространения программных компонентов. Программа обеспечивает централизованное управление зависимостями при разработке и сборке программного обеспечения.

### 1.1. Назначение

- Хранение и раздача артефактов по протоколам Docker (OCI), npm, Maven, PyPI, Cargo, Helm OCI и Raw.
- Проксирование и кэширование внешних репозиториев для ускорения сборок и обеспечения доступности при отсутствии соединения с сетью Интернет.
- Контроль целостности артефактов посредством верификации SHA-256.
- Аудит и протоколирование всех операций.

### 1.2. Системные требования

| Параметр | Минимальные | Рекомендуемые |
|----------|-------------|---------------|
| ОС | Linux (amd64, arm64) | Ubuntu 22.04+, RHEL 8+ |
| ЦПУ | 1 ядро | 2+ ядра |
| ОЗУ | 256 МБ | 1+ ГБ |
| Диск | 1 ГБ | 50+ ГБ (зависит от объёма хранимых артефактов) |
| Сеть | TCP-порт (по умолчанию 4000) | — |

### 1.3. Зависимости

Программа поставляется как единый статически слинкованный исполняемый файл. Внешние зависимости отсутствуют. Перечень библиотек, включённых в состав программы, приведён в файле `nora.cdx.json` (формат CycloneDX).

## 2. Установка

### 2.1. Автоматическая установка

```bash
curl -fsSL https://getnora.dev/install.sh | bash
```

Скрипт выполняет следующие действия:

1. Определяет архитектуру процессора (amd64 или arm64).
2. Загружает исполняемый файл с GitHub Releases.
3. Создаёт системного пользователя `nora`.
4. Создаёт каталоги: `/etc/nora/`, `/var/lib/nora/`, `/var/log/nora/`.
5. Устанавливает файл конфигурации `/etc/nora/nora.env`.
6. Устанавливает и активирует systemd-сервис.

### 2.2. Ручная установка

```bash
# Загрузка
wget https://github.com/getnora-io/nora/releases/latest/download/nora-linux-amd64
chmod +x nora-linux-x86_64
mv nora-linux-x86_64 /usr/local/bin/nora

# Создание пользователя
useradd --system --shell /usr/sbin/nologin --home-dir /var/lib/nora --create-home nora

# Создание каталогов
mkdir -p /etc/nora /var/lib/nora /var/log/nora
chown nora:nora /var/lib/nora /var/log/nora

# Установка systemd-сервиса
cp dist/nora.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable nora
```

### 2.3. Установка из Docker-образа

```bash
docker run -d \
  --name nora \
  -p 4000:4000 \
  -v nora-data:/data \
  --stop-timeout 30 \
  ghcr.io/getnora-io/nora:latest
```

**Срок остановки.** `docker stop` по умолчанию ждёт 10 секунд, а NORA при остановке даёт
открытым запросам до 15 секунд и планировщикам ещё до 10 (п. 4.1). Без `--stop-timeout 30`
(в Compose — `stop_grace_period: 30s`) контейнер убивается по SIGKILL с кодом 137, и журнал
аудита и `last_used` токенов не сбрасываются.

**Код выхода 78 и политика перезапуска.** 78 — ошибка конфигурации: перезапуск её не
исправит. С `--restart unless-stopped` или `always` контейнер уходит в бесконечный цикл
перезапусков: если он в состоянии `Restarting`, причина — в `docker logs`, исправьте
конфигурацию. `on-failure:N` ограничит число попыток, но такой контейнер не поднимется
после перезапуска Docker или перезагрузки хоста.

**Смена варианта образа на том же томе.** Пользователь `nora` в образе на Alpine имеет uid
100, в образах RED OS (`-redos`) и Astra (`-astra`) — uid 999 (проверить: `docker run --rm
--entrypoint id <образ>`). При переходе между ними на том же томе NORA не может прочитать свои
файлы и не стартует (`Permission denied` на ключ подписи). Перед сменой выполните
`chown -R <uid>:<gid>` каталога данных под новый образ или запустите контейнер с `--user`
прежнего uid.

## 3. Конфигурация

Конфигурация задаётся через переменные окружения, файл `config.toml` или их комбинацию. Приоритет: переменные окружения > config.toml > значения по умолчанию.

### 3.1. Основные параметры

| Переменная | Описание | По умолчанию |
|-----------|----------|--------------|
| `NORA_HOST` | Адрес привязки | `127.0.0.1` |
| `NORA_PORT` | Порт | `4000` |
| `NORA_PUBLIC_URL` | Внешний URL (для генерации ссылок) | — |
| `NORA_STORAGE_PATH` | Путь к каталогу хранилища | `data/storage` |
| `NORA_STORAGE_MODE` | Тип хранилища: `local` или `s3` | `local` |
| `NORA_BODY_LIMIT_MB` | Максимальный размер тела запроса (МБ) | `2048` |
| `NORA_SHUTDOWN_TIMEOUT` | Сколько секунд ждать завершения открытых запросов при остановке (`server.shutdown_timeout`) | `15` |
| `NORA_HEADER_READ_TIMEOUT` | За сколько секунд клиент должен прислать заголовки запроса: первого в соединении — от подключения, следующего — от его первого байта (`server.header_read_timeout`). Для HTTP/2 — за сколько секунд от подключения клиент должен открыть первый поток | `30` |
| `NORA_KEEP_ALIVE_TIMEOUT` | Сколько секунд простаивающее keep-alive соединение ждёт следующего запроса (`server.keep_alive_timeout`). Держите больше idle-таймаута прокси перед NORA (traefik — 90 с, nginx — 60 с); 90 и меньше — предупреждение при старте. Для HTTP/2 — сколько секунд соединение без открытых потоков ждёт нового, затем NORA закрывает его (GOAWAY); пинги keep-alive срок не продлевают | `120` |
| `NORA_MAINTENANCE_STALL_SECS` | Через сколько секунд без законченного прохода фонового цикла обслуживания `/health` отвечает 503 (`server.maintenance_stall_secs`). Не меньше `90` — три прохода по 30 с. От него же считается срок прохода: треть того, что остаётся за вычетом одного прохода (по умолчанию 90 с) | `300` |
| `NORA_MAX_CONNECTIONS` | Предел открытых клиентских соединений; сверх него новые ждут в очереди ядра (`server.max_connections`). Держите ниже лимита открытых файлов процесса и выше числа keep-alive соединений, которые прокси перед NORA держат открытыми: простаивающее соединение тоже занимает место, и новые запросы ждут, пока прокси не закроет простаивающее (nginx — через 60 с, и за ним клиент получит 504) | `4096` |

### 3.2. Аутентификация

| Переменная | Описание | По умолчанию |
|-----------|----------|--------------|
| `NORA_AUTH_ENABLED` | Включить аутентификацию | `false` |
| `NORA_AUTH_HTPASSWD_FILE` | Путь к файлу htpasswd | `users.htpasswd` |

Создание пользователя:

```bash
htpasswd -Bc /etc/nora/users.htpasswd admin
```

Роли: `admin` (полный доступ), `write` (чтение и запись), `read` (только чтение, по умолчанию).

Пароль htpasswd проверяется bcrypt вне рабочих потоков сервера, и результат проверки запоминается
до перезапуска: повторный запрос с тем же именем и паролем (в том числе API-токен, переданный
паролем Basic от имени пользователя htpasswd) bcrypt не платит. Изменения файла htpasswd
вступают в силу после перезапуска. На открытых путях (`/health`, `/ready`, открытый веб-интерфейс)
bcrypt не запускается вовсе: заголовок Basic там учитывается, только если эти имя и пароль уже
прошли проверку на закрытом пути.

**OIDC для CI (GitHub Actions, GitLab CI).** Каждый провайдер в `[[auth.oidc.providers]]`
обязан назвать `audience` — значение `aud`, которое запрашивают задания CI. Без него NORA
приняла бы токен, выпущенный тем же иссуером для любого другого сервиса, а у GitHub Actions
иссуер один на все репозитории GitHub. Включённый провайдер без `audience` NORA не запускает
(код выхода 78) и не применяет такую перезагрузку по SIGHUP; сообщение называет провайдера:

```toml
[[auth.oidc.providers]]
name = "github-actions"
issuer = "https://token.actions.githubusercontent.com"
audience = "nora"   # в задании: core.getIDToken('nora') / id_tokens: … aud: nora
```

Если иссуер не выпускает `aud`, который можно назвать, проверку отключают явно:
`any_audience = true` вместо `audience`. Тогда NORA принимает токен с любым `aud` и при каждом
старте пишет предупреждение с именем провайдера. `any_audience = true` рядом с `audience`
ничего не меняет: проверяется `audience`, а при старте пишется, что ключ проигнорирован.
Переменной окружения у этих ключей нет, как и у других ключей провайдера.

### 3.3. Проксирование внешних репозиториев

| Переменная | Описание | По умолчанию |
|-----------|----------|--------------|
| `NORA_NPM_PROXY` | URL npm-реестра | `https://registry.npmjs.org` |
| `NORA_NPM_PROXY_AUTH` | Учётные данные (`user:pass`) | — |
| `NORA_NPM_METADATA_TTL` | TTL кэша метаданных (секунды) | `300` |
| `NORA_PYPI_PROXY` | URL PyPI-реестра | `https://pypi.org/simple/` |
| `NORA_MAVEN_PROXIES` | Список Maven-репозиториев через запятую | `https://repo1.maven.org/maven2` |
| `NORA_DOCKER_PROXIES` | Docker-реестры (quick start), через запятую `url\|auth\|prefix\|ns1;ns2` — поля после `url` необязательны | `https://registry-1.docker.io` |
| `NORA_DOCKER_DEFAULT_ACTION` | Для имён, которые не направлены ни `prefix`, ни `namespaces`, ни хостом реестра: `allow` — цепочка upstreams без `namespaces` по порядку, `deny` — `403 DENIED` | `allow` |
| `NORA_DOCKER_MISS_TTL` | Секунды, в течение которых тег, которого нет ни у одного upstream, отвечается `404` без нового запроса к upstream; `0` — выключено. Push такого тега отвечает сразу (#1192) | `30` |

> **Рекомендация для production.** Для Docker-прокси с аутентификацией используйте `config.toml` вместо переменной окружения. Это позволяет хранить учётные данные отдельно (например, в Kubernetes Secret, смонтированном как файл) и упрощает ротацию токенов.
>
> ```toml
> [[docker.upstreams]]
> url = "https://private.registry.io"
> auth = "user:token"
> namespaces = ["team-*"]   # team-a/service — только отсюда
>
> [[docker.upstreams]]
> url = "https://registry-1.docker.io"
> ```
>
> Приватный реестр без `namespaces` стоит в общей цепочке: имя, которого в нём нет или на которое он ответил `401`, будет взято у следующего upstream — например, одноимённый образ с Docker Hub. `namespaces` отдаёт имена с этим первым сегментом только приватному реестру, его ответ окончательный. Подробнее — раздел «Маршрутизация» страницы Docker-прокси в документации.

**Окно свежести тегов по upstream.** Теги, которые NORA взяла у upstream, перепроверяются у него при каждом pull, если окно не задано. Окно задаёт `[docker] metadata_ttl` (`NORA_DOCKER_METADATA_TTL`, по умолчанию `-1`, то есть перепроверять всегда). Каждый `[[docker.upstreams]]` может задать своё `metadata_ttl` в тех же значениях: положительное число — секунды, в течение которых копия тега отдаётся из кэша без обращения к upstream; ноль или отрицательное значение — перепроверять при каждом pull. Копия берёт окно того upstream, в чьём пространстве хранения (`namespace`) она лежит; upstream без своего ключа живёт по глобальному значению, поэтому конфиг без нового ключа ведёт себя как прежде. Копия из общей цепочки (без `prefix` и `namespaces`) хранится под пространством первого upstream цепочки и берёт его окно.

```toml
[docker]
metadata_ttl = 3600              # по умолчанию: копии тегов отдаются из кэша час

[[docker.upstreams]]
url = "https://registry-1.docker.io"
metadata_ttl = 60                # теги Docker Hub, например latest, перепроверяются через минуту

[[docker.upstreams]]
url = "https://registry.internal.example"
metadata_ttl = 86400             # закреплённый внутренний реестр: его теги не меняются, кэш на сутки
```

**Теги, которых нет.** Если ни один upstream не знает тега, NORA запоминает это на `NORA_DOCKER_MISS_TTL` секунд (`[docker] miss_ttl`, по умолчанию `30`) и отвечает `404` без новых запросов к upstream: CI-цикл по отсутствующему образу не умножает нагрузку на реестр и не доводит его до rate-limit. Одновременные запросы к одному такому тегу делят один раунд запросов к upstream. Запоминается только ответ «не найдено» от всех upstream: если хоть один упал, отказал в доступе или ограничил частоту запросов, промах не запоминается. Тег, который вы запушили в NORA, отвечается сразу. Теги `sha256-…` (referrers) не запоминаются никогда. Значение `0` выключает запоминание; совместное ожидание одного запроса остаётся.

### 3.4. Ограничение частоты запросов

| Переменная | Описание | По умолчанию |
|-----------|----------|--------------|
| `NORA_RATE_LIMIT_ENABLED` | Включить ограничение | `true` |
| `NORA_RATE_LIMIT_GENERAL_RPS` | Запросов в секунду (общие) | `100` |

## 4. Управление сервисом

### 4.1. Запуск и остановка

```bash
systemctl start nora       # Запуск
systemctl stop nora        # Остановка
systemctl restart nora     # Перезапуск
systemctl status nora      # Статус
journalctl -u nora -f      # Просмотр журнала
```

**Остановка не ждёт бесконечно.** По SIGTERM/SIGINT NORA перестаёт принимать новые
соединения и даёт открытым запросам `NORA_SHUTDOWN_TIMEOUT` секунд (по умолчанию `15`).
Соединения, открытые по истечении этого времени, закрываются, в журнал пишется
предупреждение `Connections still open after the shutdown timeout are closed`, и остановка
продолжается: фоновые планировщики получают ещё до 10 секунд, затем сбрасываются журнал
аудита и `last_used` токенов. Без этого предела клиент, переставший читать ответ, держал
процесс до принудительного убийства оркестратором, и эти шаги не выполнялись.

Значение по умолчанию выбрано так, чтобы вместе с ожиданием планировщиков уложиться в
стандартные 30 секунд `terminationGracePeriodSeconds` в Kubernetes. Если увеличиваете
`NORA_SHUTDOWN_TIMEOUT`, увеличьте и grace period, иначе под будет убит до завершения.

**Обновление пакета сохраняет состояние службы.** `apt upgrade` и `dnf upgrade` не
выключают реестр: работавший экземпляр пакет перезапускает после распаковки
(`systemctl try-restart`, чтобы подхватить новый бинарь), а остановленный
администратором остаётся остановленным. Автозапуск (`systemctl disable`) снимается
только при настоящем удалении пакета. До версии 1.3.3 обновление останавливало службу
и не поднимало её обратно.

**Откат на предыдущую версию.** Версия 1.4.2 и раньше не знают ключей `[server]`
`header_read_timeout`, `keep_alive_timeout`, `max_connections` и `maintenance_stall_secs`.
Обычно такой ключ даёт предупреждение и игнорируется, но с `NORA_CONFIG_STRICT=true`
старая версия отказывается стартовать (код выхода 78, systemd не перезапускает). Перед
откатом уберите эти ключи из `config.toml` или задайте их переменными окружения
(`NORA_HEADER_READ_TIMEOUT` и т. д.) — неизвестные переменные старая версия не читает.

**Обновление с 1.4.2 и раньше: OIDC-провайдер без `audience`.** Раньше NORA с таким
провайдером стартовала без предупреждения и принимала токен с любым `aud`; теперь NORA с ним не
стартует. Перед обновлением задайте каждому включённому провайдеру `audience` (значение,
которое запрашивают задания CI) или, если проверка `aud` действительно не нужна,
`any_audience = true`. Откат на 1.4.2 с `any_audience = true` в файле: старая версия
предупреждает о неизвестном ключе и принимает любой `aud`, как и раньше, а с
`NORA_CONFIG_STRICT=true` не стартует — уберите ключ перед откатом.

### 4.2. Проверка работоспособности

```bash
curl http://localhost:4000/health
```

Ответ при нормальной работе:
```json
{
  "status": "healthy",
  "version": "1.0.0",
  "storage": { "backend": "local", "reachable": true },
  "registries": { "docker": "ok", "npm": "ok", "maven": "ok", "cargo": "ok", "pypi": "ok" }
}
```

`/health` — проба живости: недоступное хранилище его не роняет (`"status": "degraded"`, код 200),
для этого есть `/ready`. Код 503 и `"status": "unhealthy"` `/health` отдаёт, только если фоновый
цикл обслуживания (истечение сессий загрузки, проверка доступности хранилища; он же запускает
сброс `last_used` токенов и подсчёт размера хранилища)
не закончил ни одного прохода дольше `NORA_MAINTENANCE_STALL_SECS` (по умолчанию 5 минут; каждый
проход падает или цикл перестал начинать новые): такой процесс исправляет только перезапуск, и
Kubernetes перезапустит под по liveness-пробе. Доступность хранилища проход проверяет одним
дешёвым запросом (на объектном хранилище — первая страница листинга, на локальном диске — пробная
запись: создать, записать, fsync и удалить файл в каталоге хранилища), а размер хранилища считается
отдельной задачей, сколько бы ни занял полный листинг или обход каталога: большой бакет на `/ready` не влияет. Проход, который ждёт хранилище, прерывается по
сроку (треть того, что окно оставляет за вычетом одного прохода, по умолчанию 90 с), в журнал
пишется предупреждение `maintenance tick cut at its deadline`, растёт
`nora_maintenance_timeouts_total`, а следующий проход начинается по расписанию: `/health`
остаётся 200, `/ready` отвечает 503, пока хранилище не ответит, и снова 200 без перезапуска.

Сами `/health` и `/ready` хранилище не трогают ни на одном бэкенде: они отдают вердикт последнего
прохода. Поэтому диск, перемонтированный только на чтение, или заполненный диск переводит `/ready`
в 503 не позже чем через период прохода (30 с), а `/health` остаётся 200. Если диск перестал
отвечать, проход прерывается по сроку и `/ready` отвечает 503 со следующего прохода; зависшую
пробную запись следующий проход не повторяет. Вердикт старше 150 с (пять проходов) считается
недоступностью, так что остановившийся цикл тоже снимает готовность. Сразу после старта, до первого
прохода, `/ready` отвечает 503. Размер хранилища в `/health` (`total_size_bytes`) — результат
последнего подсчёта задачи `storage_size` (раз в 60 с), а не обход каталога на каждый запрос.
Под Docker и systemd без оркестратора код 503
сам перезапуска не вызывает, это нужно настроить:

- Docker: `HEALTHCHECK` образа (`nora healthcheck`, ненулевой код при 503) помечает контейнер
  `unhealthy`, но `restart: unless-stopped` на это не реагирует. Перезапуск по статусу
  делает Swarm (`docker service`) или наблюдатель вроде `willfarrell/autoheal`.
- systemd: `Restart=on-failure` срабатывает только при выходе процесса. Для 503 добавьте
  таймер, который раз в минуту выполняет `nora healthcheck || systemctl restart nora`.

Паника при обработке запроса даёт этому запросу ответ 500, остальные запросы обслуживаются.
Паника долгоживущей фоновой задачи (цикл обслуживания, сброс статистики pull, сборка мусора и
ретеншн, перечитывание политики по SIGHUP, а также запускаемые циклом обслуживания сброс
`last_used` токенов `token_flush` и подсчёт размера хранилища `storage_size`) пишется в журнал как `background task panicked` с
именем задачи и считается в метрике `nora_task_panics_total{task}`; задача перезапускается с
нарастающей паузой. Если она падает снова и снова, `/health` отвечает 503 и называет её в поле
`failing_task`. Паника писателя журнала аудита завершает процесс с кодом 70: без аудита NORA
не работает, systemd и оркестратор перезапустят процесс.

### 4.3. Метрики (Prometheus)

```
GET /metrics
```

Экспортируются: количество запросов, латентность, загрузки и выгрузки по протоколам.


### 5.2. Восстановление

```bash

```

### 5.3. Сборка мусора и политики хранения

```bash
nora gc                       # Просмотр: что будет удалено (без удаления)
nora gc --apply               # Удаление осиротевших блобов
nora retention-plan           # Просмотр: какие версии удалят политики хранения
nora retention-apply --yes    # Удаление старых версий по политикам хранения
```

**Хранилище, с которым работает сервер, чистит сам сервер.** Запущенный сервер выполняет
сборку мусора и политики хранения по расписанию: `[gc] enabled = true` (`NORA_GC_ENABLED`,
интервал `NORA_GC_INTERVAL`, по умолчанию сутки) и `[retention] enabled = true`
(`NORA_RETENTION_ENABLED`, интервал `NORA_RETENTION_INTERVAL`). Первый проход выполняется при
старте. Удаления сервера идут в том же процессе, что и загрузки, и берут блокировки публикации
по ключам удаляемых файлов.

Команды `nora gc --apply` и `nora retention-apply --yes` — отдельный процесс со своими
блокировками. Их удаления не упорядочены с публикациями работающего сервера: публикация,
совпавшая с удалением того же артефакта, может потерять файлы. Сборку мусора от
только что загруженных блобов защищает окно `NORA_GC_GRACE` (по умолчанию 7 дней), политики
хранения такого окна не имеют. Запускайте эти команды при остановленном сервере
(`systemctl stop nora`) или на хранилище, с которым сервер не работает. Просмотры (`nora gc`,
`nora retention-plan`, `nora retention-apply` без `--yes`) ничего не удаляют и безопасны при
работающем сервере.

Перед удалением команда проверяет, работает ли сервер на том же хранилище, и, если да, пишет
одну строку `warning: a NORA server is running on this storage; …` в stderr. Команда при этом не
останавливается. На локальном диске признак — блокировка (`flock`), которую каждый сервер держит
на своём каталоге в `.nora-staging/` от старта до выхода; ядро снимает её с завершением
процесса, поэтому каталог, оставшийся после аварийно завершённого сервера, предупреждения не
вызывает. Объектное хранилище (S3, GCS) такого признака не хранит, поэтому команда всегда
пишет `warning: … cannot tell whether a NORA server is running on this storage; …`.
Каталог `.nora-staging/`, который команда не может прочитать целиком, тоже даёт
предупреждение «cannot tell». Двух серверов команда не увидит: сервер, который стартовал без
каталога в `.nora-staging/` (в его журнале при старте есть строка `No staging directory`), и
сервер на другой машине с тем же локальным томом по NFS (`flock` по NFS зависит от настроек
монтирования). Поэтому отсутствие предупреждения не заменяет остановку сервера.

## 6. Предварительное кэширование (nora mirror)

Команда `nora mirror` позволяет заранее загрузить зависимости через прокси-кэш NORA.

**Подготовка к работе без доступа к сети Интернет.** Для каждого формата ниже `nora mirror`
загружает то, что клиент читает без сети. Затем перенесите хранилище в изолированную среду
резервной копией (раздел 5).

`nora mirror pip` загружает все файлы закреплённой версии каждого требования (`имя==версия`):
каждый wheel и архив исходников, потому что платформа и версия Python будущего клиента
неизвестны. Требование без точной версии (`>=`, `~=`, `==1.*` или без версии) команда не
загружает, а сообщает о нём и завершается ошибкой. Зависимости требований команда не
вычисляет, поэтому перечислите их все с закреплёнными версиями: `pip freeze > requirements.txt`
или `pip-compile`. Индекс PyPI NORA при каждом запросе берёт у внешнего репозитория; без сети
индекс собирается из уже загруженных файлов пакетов.

`nora mirror go --modfile go.mod` загружает то, что `go mod download` читает без сети. Для
каждого модуля из `require` в go.mod команда загружает файлы `.info`, `.mod` и `.zip`. Директивы
`replace` учитываются: вместо модуля загружается его замена, а модуль, заменённый каталогом,
пропускается. Файл go.sum рядом с go.mod (или указанный в `--sumfile`) добавляет перечисленные в
нём версии. Для версии с хешем модуля загружаются все три файла, для версии только с хешем
`/go.mod` загружается один `.mod`: Go читает его, чтобы построить граф модулей. Исключение —
go.mod со строкой `go` ниже 1.17 или вовсе без неё: тогда `go mod download` скачивает все модули
графа, и для каждой версии из go.sum загружаются все три файла. Каталог в `replace` можно указать
в кавычках, в том числе с пробелом (`=> "../local module"`). Если в `require` вместо версии стоит
ветка, тег или коммит (`vnext`, `master`), команда узнаёт версию из ответа `.info` и загружает
файлы этой версии, как это делает Go. Запросы, которые Go разрешает по списку версий (`latest`,
`v1`, `v1.2`), команда не принимает и предлагает выполнить `go mod tidy`. Без go.sum офлайн-загрузка
обычно не проходит, поэтому сначала выполните `go mod tidy`. Если файл не удалось загрузить,
команда называет модуль и завершается ошибкой. Клиенту укажите `GOPROXY=http://<адрес NORA>/go`.

`nora mirror docker` загружает образ целиком: для многоплатформенного образа — все платформы
и аттестации, которые перечислены в его индексе, поэтому места он занимает больше, чем один
`docker pull`.

`nora mirror cargo` загружает для каждого пакета из `Cargo.lock` запись sparse-индекса и архив
`.crate`.

### 6.1. Кэширование по lockfile

```bash
nora mirror npm --lockfile package-lock.json --registry http://localhost:4000
nora mirror pip --lockfile requirements.txt --registry http://localhost:4000
nora mirror cargo --lockfile Cargo.lock --registry http://localhost:4000
nora mirror go --modfile go.mod --registry http://localhost:4000
```

### 6.2. Кэширование по списку пакетов

```bash
nora mirror npm --packages lodash,express --registry http://localhost:4000
nora mirror npm --packages lodash --all-versions --registry http://localhost:4000
```

### 6.3. Параметры

| Флаг | Описание | По умолчанию |
|------|----------|--------------|
| `--registry` | URL экземпляра NORA | `http://localhost:4000` |
| `--concurrency` | Количество параллельных загрузок | `8` |
| `--all-versions` | Загрузить все версии (только с `--packages`) | — |

## 8. Безопасность

### 8.1. Контроль целостности

При проксировании npm-пакетов NORA вычисляет и сохраняет контрольную сумму SHA-256 для каждого тарбола. При повторной выдаче из кэша контрольная сумма проверяется. В случае расхождения запрос отклоняется, а в журнал записывается предупреждение уровня SECURITY.

### 8.2. Защита от подмены пакетов

- Валидация имён файлов при публикации (защита от обхода каталогов).
- Проверка соответствия имени пакета в URL и теле запроса.
- Иммутабельность версий: повторная публикация той же версии запрещена.

### 8.3. Аудит

Все операции (загрузка, выгрузка, обращения к кэшу, ошибки) фиксируются в файле `audit.jsonl` в каталоге хранилища. Формат — JSON Lines, одна запись на строку.

### 8.4. Усиление systemd

Файл сервиса содержит параметры безопасности:

- `NoNewPrivileges=true` — запрет повышения привилегий.
- `ProtectSystem=strict` — файловая система только для чтения, кроме указанных каталогов.
- `ProtectHome=true` — запрет доступа к домашним каталогам.
- `PrivateTmp=true` — изолированный каталог временных файлов.

## 10. Устранение неполадок

### Сервис не запускается

```bash
journalctl -u nora --no-pager -n 50
```

Частые причины: занят порт, недоступен каталог хранилища, ошибка в конфигурации.

### Прокси-кэш не работает

1. Проверьте доступность внешнего реестра: `curl https://registry.npmjs.org/lodash`.
2. Убедитесь, что переменная `NORA_NPM_PROXY` задана корректно.
3. При использовании приватного реестра укажите `NORA_NPM_PROXY_AUTH`.

### Ошибка целостности (Integrity check failed)

Контрольная сумма кэшированного тарбола не совпадает с сохранённой. Возможные причины: повреждение файловой системы или несанкционированное изменение файла. Удалите повреждённый файл из каталога хранилища — NORA загрузит его заново из внешнего реестра.
